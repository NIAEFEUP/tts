# Database — Prisma 8 internals

Deep reference for the TTS backend database. Setup and the everyday commands live in the
[repo README](../../../README.md#database); this page covers the migration model and recovery
paths for when things go wrong.

The DB schema and runtime client live in `src/infrastructure/database/`:

| File              | Purpose                                                     |
| ----------------- | ----------------------------------------------------------- |
| `contract.prisma` | The schema — the source of truth. Edit this.                |
| `contract.json`   | Generated by `contract:emit`. Do not edit. **Git-ignored.** |
| `contract.d.ts`   | Generated by `contract:emit`. Do not edit. **Git-ignored.** |
| `prisma.ts`       | Runtime client. Import `db` from here in your repositories. |

## Changing the schema

Every schema change follows this loop:

```
edit contract.prisma → contract:emit → (dev: db:update) or (shared/prod: plan → migrate)
```

### Quick path — local dev only

Applies the diff directly without writing a migration file.

```bash
# 1. edit contract.prisma
bun run contract:emit          # 2. regenerate artefacts
bun run db:update              # 3. apply directly to your local DB (no history written)
```

> ⚠️ Never use `db:update` against a shared or production database. It leaves no migration history
> and cannot be replayed.

### Formal path — shared environments and production

```bash
# 1. edit contract.prisma
bun run contract:emit          # 2. regenerate artefacts
bun run migration:plan -- --name <slug>   # 3. diff contract vs. last known DB state
# 4. review the generated files (below)
bun run migrate                # 5. apply the migration
```

Each `migration:plan` writes a directory like:

```
migrations/app/
└── 20261001T1200_add_users_table/
    ├── migration.json   ← manifest (hash, from/to contract hashes)
    ├── ops.json         ← canonical operation list (do not edit directly)
    └── migration.ts     ← TypeScript source you can review (and edit for data transforms)
```

Inspect before applying:

```bash
bun run migration:show -- 20261001T1200_add_users_table   # one package
bun run migrate:show                                      # full ordered plan (no writes)
```

## Data transforms (backfills)

When you add a `NOT NULL` column with no default, the planner cannot know how to backfill existing
rows and leaves a `placeholder(...)` in `migration.ts`.

**Signs you need a data transform:**

- `bun run migration:plan` output shows `pendingPlaceholders: true`
- `bun run migrate` throws `MIGRATION.UNFILLED_PLACEHOLDER`

**How to fill it:**

1. Open the generated `migration.ts`.
2. Replace the `() => placeholder("slot-name")` arrows with real query closures built against
   `endContract` (the end-state client).
3. Self-emit the package:

   ```bash
   node migrations/app/<dir>/migration.ts
   ```

4. Apply:

   ```bash
   bun run migrate
   ```

## Migration mental model

Prisma 8's migration graph is a set of **edges** between contract hashes — there is no implicit
"tip" or "head", so the planner needs to know where to start.

**The `db` ref** (`migrations/app/refs/db.json`) points at the contract hash your local database was
last brought to. `db:update` and `db:init` write it automatically; `migration:plan` reads it as the
default origin.

```
db:init / db:update  →  writes db ref
migration:plan       →  reads db ref as origin, writes new migration dir
migrate              →  applies pending migrations, advances the DB marker
```

**Important:** after a plain `bun run migrate` the `db` ref lags behind. Refresh it with
`bun run db:update` (a no-op on the DB if already current), or use `--advance-ref db` during migrate.

## Diagnostics

```bash
bun run migration:status   # pending / applied migration state
bun run db:verify          # verify the DB matches the contract (0 = clean, 4 = drift)
bun run db:schema          # inspect the live DB schema
bun run db:sign            # re-sign the marker after a manual DB fix
```

Use `db:verify` after manual SQL edits, restores, or failed migrations.

## Recovering from common errors

| Error                            | Cause                                           | Fix                                                               |
| -------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| `MIGRATION.HASH_MISMATCH`        | `migration.ts` was edited without self-emitting | `node migrations/app/<dir>/migration.ts`, then `bun run migrate`  |
| `MIGRATION.UNFILLED_PLACEHOLDER` | Placeholder not filled in `migration.ts`        | Fill the transform, self-emit, then `bun run migrate`             |
| `MIGRATION.PLAN_ORIGIN_UNKNOWN`  | No `db` ref and migrations already exist        | Run `bun run db:update` to reset the ref, or pass `--from <hash>` |
| `MIGRATION.HASH_NOT_IN_GRAPH`    | `db` ref points past the graph                  | `bun run migration:ref:set -- db <hash>`, then re-plan            |
| `CONTRACT.MARKER_MISSING`        | DB has no marker (fresh DB or wipe)             | `bun run db:init`                                                 |
| `CONTRACT.MARKER_MISMATCH`       | DB is at a different contract version           | Migrate forward, or `bun run db:sign` if the DB is correct        |
